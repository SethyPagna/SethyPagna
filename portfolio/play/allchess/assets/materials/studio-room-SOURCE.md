# Prepared studio lighting

`public/assets/materials/studio-room.hdr` contains the prefiltered CubeUV atlas from Three.js **0.186.0** `RoomEnvironment`, generated by `PMREMGenerator.fromScene(environment, 0.04)` with the original defaults: size 256, near 0.1, far 100, camera position `(0, 0, 0)`. It replaces repeating that calculation in the browser. The scene's separate environment intensity remains a runtime setting; it is not multiplied into this asset.

The source is the installed [Three.js RoomEnvironment](https://github.com/mrdoob/three.js/blob/r186/examples/jsm/environments/RoomEnvironment.js), using [PMREMGenerator](https://github.com/mrdoob/three.js/blob/r186/src/extras/PMREMGenerator.js). No external artwork, downloaded environment map, gamma correction, exposure adjustment, tone mapping, or sRGB conversion is baked into the pixels.

## Reproduce and validate

From the repository root, using the existing installed dependencies and browser:

```sh
node ops/scripts/assets/prepare-studio-environment.ts
node ops/scripts/assets/prepare-studio-environment.ts --channel chrome
```

The default uses Playwright's bundled Chromium; `--channel chrome` selects installed system Chrome. Run with the project's Node version, which natively strips TypeScript types before the browser function is serialized with `toString()`. The script refuses other Three.js versions, bundles the installed Three code with esbuild in memory, blocks network requests, and closes its dedicated browser in `finally`. It writes the HDR and `ops/assets/materials/studio-room-source.json` only after validation succeeds. JSON output reports numerical errors, browser/GPU identity, and measured timings. GPU/driver differences can change low-order source pixels, so regeneration is a reviewed asset change, not a promise of byte-identical output on every GPU.

The source JSON records the parameters, dimensions, byte count, SHA-256 and 24 original half-float RGB probes, spanning the six base faces and smaller mip regions. Probe coordinates are **top-down atlas coordinates**, and values come from the render target before RGBE encoding.

## Storage and loading

- Atlas: **768 × 1024**, including the complete original roughness/mip layout. This is a CubeUV atlas, not an equirectangular panorama.
- Encoding: standard Radiance `FORMAT=32-bit_rle_rgbe`, scanline header `-Y 1024 +X 768`, canonical 256-scale truncated RGB mantissas and shared power-of-two exponent.
- Orientation: WebGL readback is bottom-up; the writer reverses rows to store top-down scanlines. Keep `HDRLoader`'s default **`flipY: true`** when uploading.
- Runtime metadata: `CubeUVReflectionMapping`, `HalfFloatType`, `LinearSRGBColorSpace`, linear min/mag filters, clamp wrapping, and no generated mipmaps. `HDRLoader` supplies these defaults except the CubeUV mapping. Do not run PMREM generation again or assign an equirectangular mapping.
- Only RGB carries lighting. Radiance does not store alpha; the loader supplies alpha 1, including unused black atlas pixels. Environment sampling uses RGB.

Three 0.186 `HDRLoader` decodes with a mantissa divisor of 255, while conventional Radiance encoding uses 256. Validation explicitly allows this small normalization difference plus RGBE quantization. For a nonzero source pixel with maximum RGB value `p`, define `b = 2^(floor(log2(p)) + 1) / 255`. Each Float32 decoded channel must differ from its original by at most `b + abs(decodedFloat) * 2^-23`; HalfFloat decoded values must be within `b + abs(decodedFloat) / 1024 + 2^-24`. Zero RGB pixels must remain zero. No relative bound is applied separately to near-zero channels sharing a bright pixel exponent.

The script checks every original RGB channel using both Float and HalfFloat `HDRLoader.parse`, then loads the encoded HDR through the actual browser `HDRLoader`, uploads it to the GPU, and copies each texel into another half-float target. Every uploaded RGB half word must equal the decoded pixel at the intended original atlas coordinate. This second check verifies upload orientation independently of the CPU decoder.
